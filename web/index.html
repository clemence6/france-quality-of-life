Où habiter ? est un projet de portfolio qui explore une question concrète : comment comparer les villes pour trouver celle qui nous correspond ? Du téléchargement des données aux graphiques interactifs, voici la démarche et les choix qui rendent l’analyse compréhensible.

Croiser le budget logement, les services du quotidien, l’air et les risques.

LE TERRAIN D’ÉTUDE11 villes françaises

Un premier périmètre d’analyse, avec des données disponibles qui varient selon la ville.

LE RÉSULTATUne exploration interactive

Une carte, des portraits de villes et des graphiques pour comprendre les compromis.

01 / LA DÉMARCHE

De la source au graphique.

Le travail commence bien avant la visualisation : il faut récupérer les données, les rapprocher et vérifier ce qu’elles permettent de comparer.

  1. 1

    Collecter

    Des scripts Python téléchargent les ventes immobilières et interrogent les API des services, de l’air, des risques et de la cartographie.

  2. 2

    Préparer

    Le code INSEE identifie la même commune dans les différentes sources. Les données sont nettoyées et les maisons séparées des appartements.

  3. 3

    Contrôler

    Les dates, les unités et les limites géographiques sont vérifiées. Une information manquante reste manquante : elle ne devient pas zéro.

  4. 4

    Restituer

    Les résultats sont organisés dans Supabase et accompagnés de leur origine. La carte et les graphiques les rendent explorables, ville par ville.

02 / LES DONNÉES

Une source pour chaque question.

Une API permet aux scripts de récupérer des informations directement auprès d’un service. Ici, chaque source répond à une question différente ; chaque indicateur garde son unité, sa date et son périmètre.

Pourquoi les données INSEE ne figurent-elles pas dans les graphiques ?

Les essais sur les données INSEE ne sont pas encore intégrés à cette version. La population, les revenus et le chômage ne sont donc pas affichés. Le comparateur officiel de territoires ↗ permet de compléter la lecture.

03 / LES CHOIX D’ANALYSE

Nettoyer les données, c’est aussi prendre des décisions.

IMMOBILIER

Éviter les prix mal calculés

Une vente peut apparaître sur plusieurs lignes ou concerner plusieurs biens. Le calcul retient les ventes décrites sur une seule ligne pour limiter les erreurs d’attribution du prix.

SERVICES

Comparer toute la commune

Un cercle autour du centre ne couvre pas tous les quartiers. Le comptage utilise les limites de la commune pour inclure les services référencés dans l’ensemble de la ville.

QUALITÉ DES DONNÉES

Distinguer zéro et inconnu

Si une API ne répond pas, cela ne signifie pas qu’il n’y a aucun service ou aucun risque. La valeur est signalée comme indisponible et aucun chiffre n’est inventé.

COMPARAISON

Garder des indicateurs séparés

Un prix, un relevé d’air et une liste de risques ne décrivent pas la même chose. Les graphiques permettent de les croiser sans fabriquer une note de « meilleure ville ».

Comment les prix immobiliers sont-ils calculés ?

Un prix médian est un repère : la moitié des ventes retenues a un prix au m² inférieur, l’autre moitié un prix supérieur. Le calcul est fait séparément pour les maisons et les appartements, dans chaque ville.

Seules les ventes de maisons ou d’appartements décrites sur une seule ligne sont conservées. Le prix et la surface doivent être renseignés et positifs. Les prix inférieurs à 200 ou supérieurs à 20 000 €/m² sont écartés pour limiter les valeurs extrêmes. Il faut au moins 10 ventes retenues pour afficher un prix médian.

Ces filtres excluent une partie des ventes, y compris des transactions réelles. Le résultat donne un repère sur les ventes retenues, pas une estimation de tous les logements de la ville. La période et le nombre de ventes restent accessibles dans les fiches et les graphiques.

Comment les contrôles peuvent-ils être vérifiés ?

Les scripts conservent la source, la date de collecte, la commune et les informations utiles au calcul. Un rapport permet de retrouver les filtres immobiliers, les stations de mesure et les réponses des API. Des tests vérifient notamment les ventes sur plusieurs lignes, les unités de l’air et les limites communales.

Une vérification technique ne garantit pas que toutes les données sont complètes. Par exemple, un service absent d’OpenStreetMap peut exister dans la réalité.

04 / LA RÉALISATION

Un projet data de bout en bout.

Collecte & préparation

Python, pandas et requests : téléchargement des fichiers, appels API, filtres et calcul des indicateurs.

Stockage & traçabilité

Supabase et PostgreSQL pour les résultats ; fichiers JSON pour conserver les sources, les dates et les contrôles.

Analyse & visualisation

HTML, CSS et JavaScript, carte MapLibre et graphiques SVG interactifs : filtres, comparaisons et accès aux valeurs détaillées.

Ce que ce projet met en pratique

Relier plusieurs sources, définir des indicateurs cohérents, documenter les choix de calcul et construire une restitution accessible. Le dashboard montre les différences entre villes et les informations qui manquent encore pour décider.

05 / AIR
