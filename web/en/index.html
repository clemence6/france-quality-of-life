01 / THE PROCESS

From source to chart.

Each step addresses a practical issue: identifying the correct municipality, avoiding misallocated prices, distinguishing missing data from zero, and retaining the information needed to understand the result.

  1. 1

    Collect

    Python scripts were developed to download DVF files and query the Overpass, OpenAQ, Géorisques and IGN APIs. A daily schedule (cron) in GitHub Actions runs these scripts to update the data in Supabase, without manual intervention. Each collection retains its source and date so figures can be traced back to their origin.

  2. 2

    Prepare

    Using Python and pandas, INSEE codes are standardised to five characters and the arrondissements of Paris, Lyon and Marseille grouped by city. Prices and floor areas are converted to numbers; sales with missing, non-numeric, zero or negative values are excluded.

  3. 3

    Validate

    Tests check calculation rules, units and municipal boundaries. For each figure displayed, the site checks that the stated source and date refer to the data used. If an update is incomplete, an alert appears in GitHub Actions with details of the problems.

  4. 4

    Present

    Results are stored in Supabase with their metadata. The map and charts were developed in JavaScript to share filters and make calculations inspectable. Firebase hosts the site.

02 / THE DATA

A source for each question.

Data comes from public files or APIs, services queried automatically by the scripts. The sources provide observations; the project defines the filters, groupings and calculations used to build the indicators below.

Why are INSEE indicators not included in the charts?

Experiments with INSEE data are not yet integrated into this version. Population, income and unemployment are therefore not shown. The official area comparison tool ↗ provides additional context.

03 / ANALYTICAL DECISIONS

Cleaning data means making choices.

HOUSING

Avoid misleading price calculations

A transaction can appear on multiple rows or involve several properties. The calculation keeps single-row transactions to reduce incorrect price attribution.

SERVICES

Cover the whole municipality

A circle around the centre misses some neighbourhoods. Counts use municipal boundaries to include mapped services throughout the city.

DATA QUALITY

Distinguish zero from unknown

An API failing to respond does not mean there are no services or hazards. The value is marked unavailable; no number is invented.

COMPARISON

Keep indicators separate

A price, an air measurement and a list of hazards describe different things. The charts bring them together without inventing a single best-city score.

How are property prices calculated?

The median price is a reference point: half of the retained transactions have a lower price per square metre, and half a higher one. Houses and apartments are calculated separately for each city.

Only house or apartment sales recorded on a single row are retained. Price and floor area must be present and positive. Prices below 200 or above 20,000 €/m² are excluded to limit extreme values. A median is shown only when at least 10 transactions remain.

These filters exclude some sales, including genuine transactions. The result is a reference for the retained sample, not a valuation of every home in the city. Dates and sample sizes remain available in city profiles and charts.

How can the checks be reviewed?

Scripts retain the source, collection date, municipality and calculation details. A report records property filters, monitoring stations and API responses. Tests cover multi-row transactions, air measurement units and municipal boundaries.

Technical checks cannot guarantee complete data. For example, a service missing from OpenStreetMap may still exist in reality.
